# tests-specs — `gophkeeper/internal/api` (HTTP-интерфейс сервера)

## 1. Общие положения

- Инструменты: `go test -v -race -cover ./...`, `net/http/httptest`, `go.uber.org/mock`.
- Одна test suite на пакет; сценарии — через `t.Run`; группы — по хендлерам и middleware (раздел 3).
- Имена тестов: `TestApi_<Хендлер>_<Сценарий>`, например `TestApi_HandleRegister_InvalidPayload`.
- Каждый защищённый эндпоинт проверяется **без** `Authorization` (→ 401) и **от чужого владельца** (→ 403).
- Пароли, токены, карты **не должны** попадать в `slog`-логи и ответы — проверяется отдельными сценариями через захват `slog.Handler`.

## 2. Моки

| Зависимость | Заменитель в тестах |
|---|---|
| `user.UserService` | gomock (MockUserService) |
| `auth` (выпуск/валидация токенов) | gomock (MockAuth) |
| `authz` | gomock (MockAuthz) |
| `sync` | gomock (MockSync) |
| `storage` / `data` / `protocol` | `data`/`protocol` — реальные (чистые); `storage` — gomock |

## 3. Группы тестов

### 3.1. Композиция и маршруты — `NewServer`, `Server.Serve`

| # | Сценарий | Ожидаемо |
|---|---|---|
| 1 | `NewServer` с валидной конфигурацией | сервер создан; все маршруты из `protocol` зарегистрированы |
| 2 | Запрос на неизвестный путь | 404, JSON-ошибка по протоколу |
| 3 | Запрос на защищённый путь без токена | 401 |

### 3.2. Middleware аутентификации — `AuthMiddleware`

| # | Сценарий | Ожидаемо |
|---|---|---|
| 1 | Валидный токен (mock `auth.Validate` → `User`) | запрос доходит до хендлера, `User` доступен в контексте |
| 2 | Заголовок `Authorization` отсутствует | 401, `ErrAuthRequired` (`errors.Is`) |
| 3 | Истёкший токен | 401, `ErrTokenExpired` |
| 4 | Подделанный токен | 401, `ErrTokenInvalid` |
| 5 | Некорректный формат заголовка (не Bearer) | 400/401 по протоколу |

### 3.3. Middleware авторизации — `AuthzMw`

| # | Сценарий | Ожидаемо |
|---|---|---|
| 1 | Владелец своих данных | доступ разрешён, 2xx |
| 2 | Чужой владелец | 403; лог записи — без раскрытия чужих данных |
| 3 | Запрещённое действие для роли/владения | 403, `ErrUnauthorized`/`ErrNotOwner` |

### 3.4. `HandleRegister` — POST /register

| # | Сценарий | Ожидаемо |
|---|---|---|
| 1 | Валидный payload (mock `user.Register` → пользователь) | 201, JSON-ответ **без пароля** |
| 2 | Невалидный payload (нет логина/пароля) | 400, ошибка валидации из `protocol` |
| 3 | Логин занят (`user` → `ErrLoginTaken`) | 409 |
| 4 | Ошибка хранилища (`user` → ошибка персистентности) | 500; в `slog` нет пароля |

### 3.5. `HandleLogin` — POST /auth/login

| # | Сценарий | Ожидаемо |
|---|---|---|
| 1 | Корректные credentials | 200 + `LoginResponse` с токеном |
| 2 | Неверный пароль | 401 (`ErrInvalidCredentials`) |
| 3 | Превышен лимит попыток | 401/429, `ErrTooManyAttempts` |
| 4 | Пользователь не найден | 401 (без раскрытия факта отсутствия аккаунта) |

### 3.6. CRUD данных — `HandleData`

| # | Действие | Сценарий | Ожидаемо |
|---|---|---|---|
| 1 | GET /data | список своих данных | 200, только данные `ownerID == userID` |
| 2 | GET /data | данных нет | 200, пустой список |
| 3 | POST /data | создание валидного объекта | 201, id в ответе |
| 4 | POST /data | чужой запрос к чужим данным | 403 |
| 5 | PUT /data/:id | редактирование своего объекта | 200 |
| 6 | PUT /data/:id | чужой id | 403 |
| 7 | PUT /data/:id | устаревшая версия | 409 (`ErrConflict`) |
| 8 | DELETE /data/:id | удаление своего объекта | 204 |
| 9 | GET/PUT/DELETE /data/:id | id не существует | 404 |

### 3.7. `HandleSync` — POST /sync

| # | Сценарий | Ожидаемо |
|---|---|---|
| 1 | Валидные локальные изменения (mock `sync.SyncUp/Down`) | 200, `SyncResponse` с дельтой с сервера |
| 2 | Конфликт версий (`sync` → `ErrConflict`) | 409 |
| 3 | Ошибка синхронизации (`sync` → `ErrSyncFailed`) | 500; повторный вызов — идемпотентен |
| 4 | Чужой владелец | 403 |

### 3.8. `HandleFetch` — GET /data/:id (передача данных владельцу по запросу)

| # | Сценарий | Ожидаемо |
|---|---|---|
| 1 | Свой id | 200, содержимое + metadata |
| 2 | Чужой id | 403 |
| 3 | Не существует | 404 |
| 4 | Бинарные данные (TypeBinary) | 200, корректная передача blob (формат по протоколу) |
| 5 | Данные карты | 200, поля карты не раскрыты до расшифровки владельцем |

### 3.9. Маппинг ошибок на HTTP-статусы (табличное покрытие)

| Ошибка / случай | Статус |
|---|---|
| Невалидный payload (`ErrInvalidPayload`) | 400 |
| `ErrAuthRequired`, `ErrTokenExpired`, `ErrInvalidCredentials`, `ErrTooManyAttempts` | 401 |
| `ErrUnauthorized`, `ErrNotOwner` | 403 |
| `ErrNotFound` (данные, пользователь) | 404 |
| `ErrConflict` (версия) | 409 |
| Внутренние ошибки | 500 + запись в `slog` |

### 3.10. Форматирование ответов (JSON по протоколу)

| # | Сценарий | Ожидаемо |
|---|---|---|
| 1 | Любой успешный ответ | валидный JSON по структурам из `protocol` |
| 2 | Ответ с ошибкой | валидный JSON с ошибочным кодом/сообщением по протоколу |
| 3 | Чувствительные поля | `password`, CVV, токен **отсутствуют** в ответах |

## 4. Дополнительные сценарии

- **Логирование:** каждый обработанный запрос — структурный `slog`-лог; без раскрытия чувствительных полей (захват `slog.Handler`).
- **Graceful shutdown:** `Serve` завершается по `http.Server.Shutdown` — активные запросы дожидаются, код возврата 0.
- **Конкурентность:** одновременные запросы к одному эндпоинту — без гонок (`go test -race`).
