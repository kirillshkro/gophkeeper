# tests-specs — `gophkeeper/internal/sync` (синхронизация данных)

## 1. Общие положения

- Инструменты: `go test -v -race -cover`, `go.uber.org/mock`, каналы/горутин для независимых операций.
- Ключевой сценарий спецификации: синхронизация данных между сервером и несколькими авторизованными клиентами одного владельца.
- Имена: `TestSync_SyncUp_...`, `TestSync_ResolveConflict_...`.
- Ключевые ошибки: `ErrConflict`, `ErrSyncFailed`, `ErrStaleVersion`, `ErrNetwork`.
- Ключевой принцип: **идемпотентность** (повторный запуск безопасен) — проверяется отдельно.

## 2. Моки

| Зависимость | Заменитель |
|---|---|
| `client.Client` (локальные изменения, локальное хранилище) | gomock (MockClient) |
| `storage.Storage` (серверное/локальное хранилище) | gomock / in-memory |
| `authz` (проверка владельца) | gomock (MockAuthz) |
| `data` | реальные (чистый пакет) |
| `security` | gomock / реальные |

## 3. Группы тестов

### 3.1. `SyncUp` — отправка локальных изменений на сервер

| # | Сценарий | Ожидаемо |
|---|---|---|
| 1 | Локальные изменения есть | отправлены на сервер, `nil` |
| 2 | Локальных изменений нет | no-op, `nil` |
| 3 | Сервер вернул конфликт (`ErrConflict`) | ошибка проброшена |
| 4 | Сетевая ошибка (`ErrNetwork`) | ошибка; повторный вызов — безопасен (идемпотентность) |
| 5 | Конфликт версий | `ErrConflict` |
| 6 | Чужой владелец (`authz` → `ErrNotOwner`) | отказ, нет утечки данных |

### 3.2. `SyncDown` — получение изменений с сервера

| # | Сценарий | Ожидаемо |
|---|---|---|
| 1 | Изменения на сервере есть | применены локально, локальное == серверное |
| 2 | Изменений нет | no-op, `nil` |
| 3 | Порядок изменений | применены в порядке версий |
| 4 | Ошибка во время загрузки (частичная) | локальные данные не повреждены (атомарность/откат) |
| 5 | Сетевая ошибка | `ErrNetwork`; повтор — безопасен |

### 3.3. Версионирование

| # | Сценарий | Ожидаемо |
|---|---|---|
| 1 | Локальная версия < серверная | локальная обновлена до серверной |
| 2 | Локальная версия > серверная (сервер устарел) | локальная выигрывает (LWW) или сервер обновлён |
| 3 | Клиент с устаревшей версией (`ErrStaleVersion`) | конфликт, локальные данные не затеряны |
| 4 | Одновременные изменения с разных клиентов | детерминированный результат (LWW/merge) |

### 3.4. Разрешение конфликтов — `ResolveConflict(a, b Item) Item`

| # | Сценарий | Ожидаемо |
|---|---|---|
| 1 | Идентичное содержимое (только разные metadata) | без конфликта (объединение metadata, детерминированно) |
| 2 | Две разные версии (LWW) | победитель — по timestamp/ID (детерминированно, воспроизводимо) |
| 3 | Разные поля изменены (merge) | объединение (union), оба изменения сохранены |
| 4 | Одна из версий пустая | непустая выигрывает |
| 5 | Одинаковый timestamp → tie-break | детерминированный (по stable key, e.g. ownerID+itemID) |
| 6 | Бинарные/карточки | без потери данных, расшифровываются |
| 7 | **Воспроизводимость:** вызов `ResolveConflict` с теми же `a`, `b` | тот же результат (детерминированность) |

### 3.5. Идемпотентность и целостность

| # | Сценарий | Ожидаемо |
|---|---|---|
| 1 | `SyncUp` дважды с одинаковыми данными | второй — no-op, данные не дублируются |
| 2 | `Sync` после ошибки | данные не повреждены, повторный вызов — безопасен |
| 3 | Повторный `Sync` (клиент уже в актуальном состоянии) | no-op, `nil` |

### 3.6. Конкурентность и многопоточность

| # | Сценарий | Ожидаемо |
|---|---|---|
| 1 | Параллельные `SyncUp`/`SyncDown` (goroutines + channels) | без гонок (`-race`), финальное состояние согласовано |
| 2 | Два клиента владельца → после синхронизации данные одинаковы | инвариант соблюдён |
| 3 | Заблокированный синхрон (lock/mutex) | нет deadlocks |

### 3.7. Безопасность

| # | Сценарий | Ожидаемо |
|---|---|---|
| 1 | Доступ к чужим данным | `ErrNotOwner` (`authz`), нет утечки |
| 2 | Данные синхронизируются только для владельца | `authz`-проверка |
| 3 | `slog`-логи | без раскрытия чувствительных данных |

## 4. Дополнительные сценарии

- **Инкрементальная синхронизация:** отправка/приём только дельта (изменения после версии X), не всё — тестируется на объём данных.
- **Гарантии целостности:** после успешной синхронизации — все клиенты имеют согласованные данные (инвариант).
- **Гарантия идемпотентности:** повторный запуск — безопасен (без потери/дуплирования данных).
