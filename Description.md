# Description.md — пакет `gophkeeper` (корень модуля)

## Назначение

Пакет `gophkeeper` — корневой пакет модуля. Он является общей документацией и
точкой входа системы GophKeeper. Пакет не содержит бизнес-логики и предназначен
для описания архитектуры, общих требований и конвенций, применяемых во всех
пакетах модуля.

## Система

GophKeeper — клиент-серверная система для безопасного хранения и синхронизации
приватных данных пользователя.

**Храняемые типы данных** (по спецификации):

- пары логин/пароль;
- произвольные текстовые данные;
- произвольные бинарные данные;
- данные банковских карт;
- произвольная текстовая метаданная информация для любого типа данных.

**Бизнес-логика сервера:**

- регистрация, аутентификация и авторизация пользователей;
- хранение приватных данных;
- синхронизация данных между несколькими авторизованными клиентами одного
  владельца;
- передача приватных данных владельцу по запросу.

**Бизнес-логика клиента:**

- аутентификация и авторизация пользователей на удалённом сервере;
- доступ к приватным данным по запросу;
- создание, редактирование и удаление данных на стороне сервера или клиента;
- формат регистрации нового пользователя;
- выбор хранилища и формат хранения данных;
- обеспечение безопасности передачи и хранения данных.

**Дополнительно:**

- клиент распространяется как CLI для Windows, Linux, Mac OS;
- клиент даёт информацию о версии и дате сборки бинарного файла.

## Архитектура

```
gophkeeper/
├── cmd/
│   ├── client/        # точка входа CLI (Windows, Linux, Mac OS)
│   └── server/        # точка входа сервера
└── internal/          # внутренние пакеты
    ├── api/           # HTTP-интерфейс сервера
    ├── auth/          # аутентификация
    ├── authz/         # авторизация доступа
    ├── cli/           # CLI-команды клиента
    ├── client/        # ядро клиента
    ├── config/        # конфигурация
    ├── data/          # модель данных
    ├── protocol/      # протокол клиент–сервер
    ├── security/      # криптография
    ├── storage/       # хранилища
    ├── sync/          # синхронизация
    ├── user/          # управление пользователями
    └── version/       # версия/дата сборки
```

- Внешним интерфейсом системы являются только `cmd/client` (CLI) и
  `cmd/server` (сервер).
- Все пакеты `internal/` — внутренние, недоступны из внешних модулей.
- Архитектура микросервисная: каждый пакет — независимый слой с чёткой
  ответственностью и зависимостями «вниз».

## Общие требования к системе

1. **Тестирование.** Код покрыт юнит-тестами не менее чем на 70%. Каждая
   экспортированная функция, тип, переменная и пакет — с исчерпывающей
   godoc-документацией.
2. **Безопасность.** Данные передаются с использованием TLS, хранятся в
   зашифрованном виде. Пароли пользователей не хранятся в открытом виде.
3. **Конвенции кода.** SOLID, DRY, возврат `(value, error)`, не более двух
   параметров у методов, логирование через `slog` (не `fmt`), обработка
   ошибок через пакет `errors`.
4. **Многопоточность.** Горутин и каналы для независимых операций (загрузка,
   синхронизация, обработка запросов).
5. **Кроссплатформенность.** Клиент — CLI для Windows, Linux, Mac OS.
6. **Размер файлов.** Не более 250 строк кода на файл; при росте — разбивать.
7. **Опционально (по спецификации):** поддержка OTP, TUI, бинарный протокол,
   интеграционные тесты, Swagger.

## Требования к корневому пакету

- Пакет содержит только документацию и общие определения модуля.
- Пакет не имеет внешних зависимостей.
- Пакет не должен содержать бизнес-логики (вся логика — в `internal/` и
  `cmd/`).
- Пакет должен быть стабильным (модулярным).
